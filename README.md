# mini-erp

[![CI](https://github.com/kang30984/mini-erp/actions/workflows/ci.yml/badge.svg)](https://github.com/kang30984/mini-erp/actions/workflows/ci.yml)

IT 유통사를 가정한 B2B 주문·출고·월 정산 미니 ERP입니다.
거래처가 마켓플레이스에서 주문하면 내부 담당자가 승인·출고하고, 월말에 거래처 등급별 리베이트를 계산해 정산을 마감합니다.

설계 내용은 [docs/DESIGN.md](docs/DESIGN.md)에 정리했습니다.

## 진행 상황

- [x] 1주차: 프로젝트 세팅, DB 스키마, 로그인
- [x] 2주차: 기준정보(상품, 거래처, 리베이트 정책), 마켓플레이스 주문
- [x] 3주차: 주문 승인·출고·반품, 월 정산 프로시저와 미리보기·마감 화면
- [x] 4주차: 정산 성능 측정과 개선, 동시성 테스트, k6 부하 테스트, GitHub Actions CI

## 실행 방법

필요한 것: Docker, JDK 21, Node.js 20 이상

```bash
# 1. DB
docker compose up -d

# 2. 백엔드 (http://localhost:8080)
cd backend
./gradlew bootRun     # Windows: gradlew.bat bootRun. 실행 시 Flyway가 스키마와 데모 데이터를 넣는다

# 3. 프론트엔드 (http://localhost:5173)
cd frontend
npm install
npm run dev
```

정산 마감은 지난달까지만 할 수 있어서, 화면에서 마감까지 해 보려면 지난달 출고 데이터를 넣어 주세요. (선택)

```bash
docker exec -i minierp-postgres psql -U minierp -d minierp < db/seed/demo_last_month.sql
```

테스트는 Testcontainers가 PostgreSQL 컨테이너를 직접 띄우기 때문에 Docker만 켜져 있으면 됩니다.

```bash
cd backend
./gradlew test        # Windows: gradlew.bat test
```

## 성능 측정 (4주차)

### 측정 방법

거래처 200곳, 상품 500개, 6개월 동안 매달 출고 라인 10만 건(총 60만 건)과 반품 1%를 만든 뒤 2026년 3월분 정산 시간을 쟀습니다.

```bash
# 1. 대량 데이터 (1~3분)
docker exec -i minierp-postgres psql -U minierp -d minierp < db/seed/perf_seed.sql

# 2. 측정. 단계마다 구조를 바꿔 3번씩 실행하고 ROLLBACK하므로 DB는 바뀌지 않음
docker exec -i minierp-postgres psql -U minierp -d minierp < db/perf/measure_settlement.sql
```

### 결과

환경: Windows 11 노트북, Intel Core i3-1315U, RAM 8GB, Docker Desktop PostgreSQL 16

| 단계 | 구조 | 처리 건수 | 소요 시간 (3회 중 중앙값) |
|---|---|---|---|
| 1 | 정산용 인덱스 없음, 상세 테이블 외래키 있음 | 약 10만 건 | 1.95초 (1.95 / 1.78 / 1.98) |
| 2 | 정산용 인덱스 추가 (V4) | 약 10만 건 | 2.27초 (2.41 / 2.27 / 2.17) |
| 3 | 상세 테이블 외래키 제거 (V5) | 약 10만 건 | **1.16초** (1.06 / 1.16 / 1.25) |

V4 구조에서 V5로 바꿔 정산 시간이 **약 49% 줄었습니다** (2.27초 → 1.16초).

### 분석

- **인덱스로는 빨라지지 않았습니다.** 오히려 0.3초 정도 느렸는데, 측정 순서나 캐시 상태에 따른 오차도 섞여 있을 수 있어서 "효과가 없었다"까지만 판단했습니다. 6개월치 주문 중 한 달치(약 17%)를 고르는 조건이라, 이 비율에서는 인덱스로 골라 읽는 것과 테이블 전체를 읽는 것의 차이가 작습니다. 주문 이력이 몇 년치로 쌓이면 전체를 읽는 비용은 계속 늘지만 한 달치를 읽는 비용은 그대로라, 인덱스는 데이터가 쌓일수록 효과가 커질 것으로 보고 유지했습니다.
- **병목은 외래키 확인이었습니다.** `EXPLAIN ANALYZE`로 단계별로 나눠 보니, 조회는 0.2초 정도인데 `settlement_detail`에 10만 행을 넣을 때 행마다 실행되는 외래키 확인 트리거 두 개가 전체 시간의 절반 이상을 차지했습니다.
- **외래키를 뺀 근거**: 상세 테이블은 프로시저만 만드는 파생 데이터이고 실행할 때마다 지우고 다시 만듭니다. 값은 이미 외래키가 걸린 원본(`sales_order`, `settlement_period`)에서만 가져오므로 잘못된 참조가 생길 경로가 없습니다. 행이 수백 건뿐인 거래처 합계 테이블(`settlement`)에는 외래키를 그대로 두었습니다.

## 동시성 검증 (4주차)

### JUnit 동시성 테스트

`ConcurrencyIntegrationTest`는 다른 테스트와 달리 테스트 트랜잭션 없이 실행합니다. 여러 스레드가 각자 트랜잭션을 커밋해야 실제로 잠금이 경쟁하기 때문입니다. 출발 신호(`CountDownLatch`)를 한 번에 줘서 최대한 동시에 실행하고, 끝나면 만든 데이터를 직접 지웁니다.

| 시나리오 | 기대 결과 |
|---|---|
| 재고 10개 상품의 1개짜리 주문 20건 동시 승인 | 10건 승인, 10건 재고 부족, 재고 0 |
| 같은 주문을 관리자 5명이 동시에 승인 | 1건만 승인, 4건은 다른 사용자가 먼저 처리함(409), 재고는 한 번만 차감 |
| 거래처 취소와 관리자 승인이 동시에 (10쌍) | 주문마다 하나만 반영, 재고 = 처음 재고 - 승인 건수 |
| 수량 5개인 줄에 1개씩 반품 10건 동시 등록 | 5건만 등록, 반품 합계 5개 |

### k6 부하 테스트

HTTP 계층(세션, CSRF, 커넥션 풀)까지 포함해서 같은 상황을 확인합니다. [k6](https://grafana.com/docs/k6/latest/set-up/install-k6/)를 설치하고 백엔드를 띄운 상태에서 실행합니다.

```bash
k6 run load-test/approve-race.js
# 규모 조절: k6 run -e ORDERS=500 -e STOCK=200 -e VUS=100 load-test/approve-race.js
```

재고 100개 상품에 주문 200건을 넣고 관리자 50명이 동시에 승인합니다. 승인 100건, 재고 부족 100건, 남은 재고 0이면 통과입니다. 테스트 데이터가 DB에 남으니 데모 DB에서 돌린 뒤에는 초기화하세요.

결과 (Docker로 k6 실행, 동시 사용자 50명):

| 항목 | 값 |
|---|---|
| 주문 / 처음 재고 | 200건 / 100개 |
| 승인 / 재고 부족(409) / 예상 외 응답 | 100건 / 100건 / 0건 |
| 남은 재고 | 0개 |
| 승인 요청 200건 처리 시간 | 3.6초 (건당 약 18ms) |
| 승인 응답 시간 | 중앙값 733ms, p95 1.08s |
| 로그인 응답 시간 | 중앙값 477ms, p95 722ms |

- 초과 판매 없이 재고만큼만 승인됐습니다.
- 승인 응답 시간이 긴 것은 모든 요청이 같은 상품 재고 행의 잠금을 차례로 기다리기 때문으로 봅니다. 처리량(건당 약 18ms)과 줄 선 순서를 곱하면 측정된 중앙값과 비슷합니다. 초과 판매를 막기 위해 의도한 직렬화이고, 같은 상품에 승인이 동시에 수십 건 몰리는 경우는 드물어서 재고 행 분할이나 큐 처리는 넣지 않았습니다.
- 로그인 응답 시간은 50명이 동시에 BCrypt 비밀번호 확인을 하면서 CPU가 몰린 영향입니다.

Docker만 있고 k6를 설치하지 않았다면 이렇게 실행할 수 있습니다. 컨테이너 안에서는 `localhost`가 컨테이너 자신을 가리키므로 `host.docker.internal`로 PC의 백엔드에 접속합니다.

```bash
docker run --rm -i -e BASE_URL=http://host.docker.internal:8080 grafana/k6 run - < load-test/approve-race.js
```

## 구현하면서 신경 쓴 부분

### 로그인 (1주차)

- **세션 + CSRF 쿠키 방식**: SPA가 `XSRF-TOKEN` 쿠키를 읽어 `X-XSRF-TOKEN` 헤더로 보냅니다. 개발 환경에서는 Vite 프록시로 같은 출처를 만들어 CORS 설정 없이 세션 쿠키를 씁니다.
- **세션 고정 방지**: 로그인에 성공하면 기존 세션 ID를 새로 발급합니다.
- **계정 존재 여부 노출 방지**: 없는 아이디, 틀린 비밀번호, 사용 중지 계정을 모두 같은 메시지로 응답합니다. Spring Security는 비밀번호 확인 전에 계정 상태를 먼저 검사하기 때문에 메시지를 나누면 비밀번호 없이도 계정 상태를 알 수 있습니다.
- **거래처 상태 연동**: 거래처가 INACTIVE가 되면 소속 사용자는 로그인할 수 없습니다. 사용자 테이블에 상태를 따로 두지 않고 조회 시 거래처 상태로 판단합니다.

### 기준정보와 주문 (2주차)

- **가격은 서버가 정한다**: 주문 요청에는 상품 ID와 수량만 받고, 단가는 DB에서 다시 읽어 계산합니다. 요청 본문에 단가를 넣어 보내도 무시됩니다.
- **거래처는 세션에서 꺼낸다**: 주문 등록·조회·취소 모두 요청 값이 아니라 로그인 세션의 거래처 ID로 범위를 제한합니다. 다른 거래처 주문은 403이 아니라 404로 응답해서 주문이 있다는 사실도 알려 주지 않습니다.
- **주문 시점 등급 저장**: 주문에 당시 거래처 등급을 복사해 둡니다. 나중에 등급을 바꿔도 지난 주문의 정산 기준은 그대로입니다.
- **조건부 UPDATE로 취소**: "상태 조회 → 변경"을 나누지 않고 `WHERE status = 'REQUESTED'` 조건을 건 UPDATE 한 번으로 취소합니다. 관리자가 같은 순간에 승인해도 둘 중 하나만 반영됩니다.
- **요율 변경은 내일부터**: 지난 날짜로 요율을 바꾸면 이미 출고된 주문의 정산이 달라지기 때문에 막았습니다. 기존 정책 종료와 새 정책 등록은 한 트랜잭션에서 잠금을 걸고 처리합니다.
- **MyBatis 세션 캐시 주의**: 같은 트랜잭션에서 같은 select를 다시 부르면 MyBatis가 캐시된 결과를 돌려줍니다. 주문번호 시퀀스와 `FOR UPDATE` 조회는 `flushCache="true"`로 캐시를 끄지 않으면 같은 번호가 다시 나오거나 잠금이 안 걸립니다.
- **검색어 이스케이프**: 검색어에 `%`나 `_`를 넣으면 와일드카드가 아니라 글자 그대로 검색되게 처리했습니다.
- **한국 시간 기준**: 서버 위치와 상관없이 날짜 계산이 한국 시간으로 되도록 `Clock` 빈과 DB 세션 시간대를 맞췄습니다.

### 주문 처리와 정산 (3주차)

- **정산은 PL/pgSQL 프로시저**: 행 단위 반복 없이 `INSERT ... SELECT` 두 번으로 상세와 합계를 만듭니다. 미리보기를 여러 번 해도 결과가 쌓이지 않고, 마감할 때도 최신 데이터로 다시 계산합니다.
- **리베이트는 출고일 요율**: 월 중간에 요율이 바뀌어도 줄마다 출고일에 적용 중이던 요율을 쓰고, 반품은 반품한 달에 원래 출고일 요율로 차감합니다.
- **정책이 빠진 주문은 정산 중단**: 조인에서 조용히 빠지면 틀린 금액으로 마감되기 때문에, 적용할 요율이 없는 주문이 있으면 주문번호를 알려 주고 멈춥니다.
- **마감월 보호 트리거**: 마감된 달의 출고·반품 데이터는 SQL을 직접 실행해도 바뀌지 않습니다. 에러 코드를 `check_violation`으로 올려서 Spring에서 `DataIntegrityViolationException`으로 받습니다.
- **잠금 순서 통일**: 승인·취소 모두 "주문 행 → 상품 행(ID 오름차순)" 순서로 잠가서 교착 상태를 피합니다.
- **낙관적 잠금**: 화면이 불러온 주문 버전을 함께 보내고, 그 사이 다른 사용자가 처리했으면 409로 알려 줍니다.
- **반품 수량 검사**: 주문 줄을 `FOR UPDATE`로 잠근 뒤 반품 합계를 **별도 문장**으로 조회합니다. 같은 문장에서 구하면 잠금을 기다리는 동안 다른 트랜잭션이 커밋한 반품이 합계에서 빠질 수 있습니다.
- **실패 로그를 별도 트랜잭션으로 남기지 않은 이유**: `REQUIRES_NEW`로 실패 기록을 넣으면, 바깥 트랜잭션이 잡고 있는 정산월 행을 안쪽이 기다리고 바깥은 안쪽을 기다리는 상태가 됩니다. 같은 스레드라 DB가 교착으로 감지하지도 못해서, 실패는 애플리케이션 로그로 남겼습니다.
- **CSV 다운로드**: UTF-8 BOM을 붙여 엑셀에서 한글이 깨지지 않게 했고, `=`, `+`, `-`, `@`로 시작하는 값은 수식으로 실행되지 않도록 처리했습니다(CSV 인젝션 방지).

### DB 제약

- 리베이트 정책은 적용 기간이 겹치면 안 됩니다. 서비스 코드에서만 막으면 동시 등록이나 직접 입력으로 깨질 수 있어서, PostgreSQL `EXCLUDE` 제약(btree_gist)으로 DB에서 막았습니다.
- 거래처 사용자는 반드시 거래처에 소속되고 관리자는 소속이 없도록 `CHECK` 제약을 걸었습니다.
