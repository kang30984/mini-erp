# ADR-008 세션 로그인과 쿠키 기반 CSRF

## 배경

화면은 React로 만든 SPA이고, 사내 관리자와 거래처 담당자가 쓴다. 로그인 상태를 어떻게 유지할지, CSRF는 어떻게 막을지 정해야 했다.

## 검토한 방법

1. JWT를 발급해서 화면이 저장하고 요청마다 헤더로 보내기
2. 서버 세션을 쓰고, CSRF 토큰은 쿠키로 내려 주고 헤더로 돌려받기

## 결정

2번으로 했다.

로그아웃, 거래처 거래 중지, 권한 변경이 바로 반영돼야 하는 업무 시스템이다. JWT는 만료 전까지 회수하기 어렵고, 화면에 저장하면 XSS에 노출된다. 세션 쿠키는 `HttpOnly`로 자바스크립트가 읽지 못하게 할 수 있다.

CSRF 토큰은 서버가 `XSRF-TOKEN` 쿠키로 내려 주고, React가 그 값을 읽어 `X-XSRF-TOKEN` 헤더로 보낸다. 다른 사이트는 브라우저 정책상 이 쿠키를 읽을 수 없어서 헤더를 만들 수 없다.

## 결과

Spring Security 6의 기본 CSRF 처리기는 BREACH 공격에 대비해 토큰을 요청마다 섞어서 비교한다. SPA는 쿠키 원본 값을 그대로 보내기 때문에 기본 처리기로는 검증에 실패한다. 그래서 원본 값을 그대로 비교하는 `CsrfTokenRequestAttributeHandler`로 바꿨다.

폼 로그인을 끄고 JSON으로 로그인을 받기 때문에, 컨트롤러에서 인증한 뒤 `SecurityContextRepository.saveContext()`를 직접 호출한다. Spring Security 6부터는 이 저장이 자동으로 되지 않아서, 빠뜨리면 로그인은 성공해도 다음 요청에서 다시 로그인이 풀린다. 로그인 직후에는 세션 ID를 새로 발급해서 세션 고정 공격을 막는다.

없는 아이디, 틀린 비밀번호, 거래 중지 계정은 같은 메시지로 응답한다. 그런데 `DaoAuthenticationProvider`는 기본적으로 비밀번호를 비교하기 전에 계정 상태부터 검사해서, 거래 중지 계정은 BCrypt 비교 없이 바로 실패했다. 메시지가 같아도 응답 시간으로 "이 아이디는 있고 거래가 중지됐다"는 걸 알 수 있었다. 그래서 사전 검사를 비우고 계정 상태 검사(`AccountStatusUserDetailsChecker`)를 비밀번호 확인 뒤로 옮겼다. 이제 모든 실패가 비밀번호 비교를 한 번씩 치르고, 계정 상태는 비밀번호를 아는 사람에게만 같은 메시지로 거절된다. 응답 시간을 직접 재는 테스트는 환경에 따라 흔들려서, 비밀번호 비교 횟수를 세는 단위 테스트(`LoginProviderTest`)로 확인한다.

개발할 때는 Vite 프록시로 화면(5173)과 API(8080)를 같은 출처로 묶는다. 그래서 CORS 설정 없이 쿠키를 그대로 쓴다. 운영에 올릴 때도 화면과 API를 같은 도메인 아래에 두는 것을 전제로 했다.

세션이 서버 메모리에 있어서 서버를 여러 대로 늘리려면 Spring Session(Redis 등)으로 옮겨야 한다.
