# ADR-001 월 정산을 PL/pgSQL 프로시저로 계산

## 배경

정산은 한 달치 출고 라인과 반품을 전부 읽어서 줄마다 리베이트를 계산하고, 거래처별로 합친 결과를 저장하는 작업이다. 거래처가 늘면 한 달에 수만~수십만 줄을 다뤄야 한다.

## 검토한 방법

1. 애플리케이션에서 출고 라인을 읽어 와 Java로 계산하고 결과를 저장하기
2. 계산은 SQL 한두 문장으로 하되, 애플리케이션에서 그 SQL을 차례로 실행하기
3. 같은 SQL을 PL/pgSQL 프로시저로 묶고, 애플리케이션은 `CALL` 한 번만 하기

## 결정

3번으로 했다.

1번은 데이터를 전부 애플리케이션으로 가져와야 해서 네트워크와 메모리를 많이 쓴다. 2번과 3번은 계산 방식은 같은데, 3번은 정산월 잠금, 마감 여부 확인, 리베이트 정책 누락 검사, 실행 이력 기록까지 한곳에 모을 수 있다. SQL을 직접 실행하는 배치나 운영자가 같은 정산을 돌려도 같은 규칙을 거친다.

## 결과

계산은 행 단위 반복 없이 `INSERT ... SELECT` 두 번으로 끝난다. 출고분과 반품분을 상세 테이블에 넣고, 상세를 다시 거래처별로 합친다.

프로시저 안에서는 `COMMIT`하지 않는다. 트랜잭션은 Spring `@Transactional`이 관리하고, 프로시저가 예외를 던지면 그 호출에서 한 작업이 전부 되돌려진다.

대신 업무 규칙 일부가 Java가 아니라 SQL에 있게 됐다. 그래서 프로시저 동작은 통합 테스트(`SettlementIntegrationTest`)로 실제 PostgreSQL에서 확인한다. 월 중간 요율 변경, 반품월 차감, 미리보기 반복, 마감 후 재실행 차단을 각각 테스트로 남겼다.

MyBatis에서 프로시저를 부를 때는 JDBC escape 문법(`{call ...}`) 대신 `CALL run_settlement(...)`를 그대로 실행한다. PgJDBC는 기본 설정에서 `{call}`을 함수 호출(SELECT)로 바꾸기 때문에 프로시저 호출이 실패한다. 같은 트랜잭션에서 뒤이어 조회하는 결과가 MyBatis 캐시에서 나오지 않도록 매퍼에서는 `<update>`로 선언했다.
