# ADR-007 반품 수량은 잠근 뒤 다음 문장에서 센다

## 배경

한 주문 줄의 반품 수량 합계는 주문 수량을 넘으면 안 된다. 관리자 두 명이 같은 줄에 동시에 반품을 등록하면, 둘 다 "아직 여유가 있다"고 판단하고 넣어 버릴 수 있다.

## 검토한 방법

1. 주문 줄을 `FOR UPDATE`로 잠그는 조회에서 반품 합계도 같이 구하기
2. 주문 줄을 잠근 뒤, 반품 합계는 다음 문장에서 따로 구하기

## 결정

2번으로 했다.

1번이 문장 하나로 끝나서 더 깔끔해 보이지만, PostgreSQL 기본 격리 수준(READ COMMITTED)에서는 맞지 않는다. 이 격리 수준은 문장마다 시작 시점의 스냅샷을 쓴다. 잠금을 기다렸다가 받으면 잠근 행 자체는 최신 값으로 다시 읽지만, 같은 문장 안의 서브쿼리는 문장이 시작할 때의 스냅샷 그대로다. 그래서 잠금을 기다리는 사이 다른 트랜잭션이 커밋한 반품이 합계에서 빠진다.

잠금을 받은 다음 문장은 새 스냅샷으로 시작하니까, 앞서 커밋된 반품까지 보인다.

## 결과

`ConcurrencyIntegrationTest`에서 수량 5개인 줄에 1개씩 반품 10건을 동시에 넣으면 5건만 등록되고 나머지 5건은 수량 초과로 거절된다.

같은 줄의 반품은 한 줄로 처리되지만, 반품이 동시에 몰리는 일은 드물어서 문제 되지 않는다고 봤다.

잠그는 조회와 합계 조회 둘 다 MyBatis 매퍼에서 `flushCache="true"`로 선언했다. 같은 트랜잭션에서 같은 조회를 다시 하면 MyBatis가 DB에 가지 않고 처음 결과를 돌려주기 때문이다.
