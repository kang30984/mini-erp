# mini-erp

[![CI](https://github.com/kang30984/mini-erp/actions/workflows/ci.yml/badge.svg)](https://github.com/kang30984/mini-erp/actions/workflows/ci.yml)

IT 제품을 유통하는 회사를 가정하고 만든 B2B 주문·월 정산 시스템이다. 거래처가 마켓플레이스에서 주문하면 내부 담당자가 승인하고 출고하며, 월말에 거래처 등급별 리베이트를 계산해서 정산을 마감한다.

화면 수를 늘리기보다는 기간계 업무에서 실제로 문제가 되는 부분에 집중했다. 마감한 달의 데이터를 어떻게 지킬지, 마감 뒤에 반품이 들어오면 어떻게 처리할지, 여러 사람이 같은 재고를 동시에 건드리면 어떻게 되는지 같은 것들이다. 중요한 결정은 [ADR](docs/adr/README.md)로 따로 정리했다.

주요 내용

- 주문 → 승인(재고 차감) → 출고 → 반품으로 이어지는 주문 처리와 상태 이력
- 월 정산을 PL/pgSQL 프로시저로 계산. 리베이트는 출고일에 적용 중이던 요율을 쓰고, 마감한 달은 DB 트리거로 변경을 막는다
- 10만 건 정산이 생각보다 느려서 원인을 찾아보니 인덱스가 아니라 외래키 확인이었다. 구조를 바꿔 실행 시간을 약 49% 줄였다 ([성능](#성능))
- 동시 승인, 승인과 취소 경합, 동시 반품, 월 경계의 마감과 출고 경합을 실제 트랜잭션으로 재현하는 테스트와 k6 부하 테스트

## 기술 스택

| 영역 | 사용 기술 |
|---|---|
| 백엔드 | Java 21, Spring Boot 3.5, Spring Security, MyBatis |
| 데이터 | PostgreSQL 16 (PL/pgSQL), Flyway |
| 프론트엔드 | React, TypeScript, Vite, React Router, TanStack Query, React Hook Form |
| 테스트 | JUnit 5, AssertJ, Testcontainers, MockMvc, k6 |
| CI | GitHub Actions (백엔드 테스트, 프론트엔드 빌드) |

MyBatis를 쓴 건 정산처럼 SQL이 핵심인 업무에서 쿼리를 직접 보고 다루고 싶었기 때문이다. 정산 자체는 애플리케이션에서 반복문으로 계산하지 않고 DB 프로시저에 맡겼다 ([ADR-001](docs/adr/001-settlement-in-plpgsql.md)).

## 실행

JDK 21, Node.js 20 이상, Docker가 필요하다.

```bash
docker compose up -d                 # PostgreSQL
cd backend && ./gradlew bootRun      # 백엔드 :8080. 처음 뜰 때 Flyway가 스키마와 데모 데이터를 넣는다
cd frontend && npm install && npm run dev   # 프론트엔드 :5173
```

http://localhost:5173 에 접속해서 아래 계정으로 로그인하면 된다. 관리자는 운영 화면으로, 거래처 사용자는 주문 화면으로 이동한다.

| 아이디 | 비밀번호 | 권한 | 소속 |
|---|---|---|---|
| admin | admin1234! | 관리자 | - |
| partner1 | partner1234! | 거래처 | 한빛시스템 (GOLD) |
| partner2 | partner1234! | 거래처 | 새솔정보통신 (SILVER) |

로컬 개발용 계정이고 `V2__seed_demo.sql`로 들어간다.

정산 마감은 지난달까지만 할 수 있다. 화면에서 마감까지 해 보려면 지난달 출고 데이터를 먼저 넣는다.

```bash
docker exec -i minierp-postgres psql -U minierp -d minierp < db/seed/demo_last_month.sql
```

마감은 되돌릴 수 없어서, 처음부터 다시 해 보려면 `docker compose down -v`로 DB를 지우고 다시 띄워야 한다.

테스트는 `./gradlew test`로 전부 돌릴 수 있다. Testcontainers가 PostgreSQL을 직접 띄우기 때문에 Docker가 켜져 있어야 한다.

### Windows (명령 프롬프트)

`./gradlew` 대신 `gradlew.bat`을 쓴다. Docker Desktop이 실행 중(Engine running)이어야 하고, `JAVA_HOME`이 JDK 21을 가리켜야 한다. 파일을 `<`로 넘기는 명령은 명령 프롬프트에서는 그대로 되지만 PowerShell에서는 지원하지 않는다.

```bat
docker compose up -d
cd backend
gradlew.bat bootRun
```

PowerShell에서 seed를 넣을 때는 이렇게 한다.

```powershell
Get-Content db\seed\demo_last_month.sql -Encoding UTF8 | docker exec -i minierp-postgres psql -U minierp -d minierp
```

실행하면서 막혔던 문제는 [트러블슈팅](docs/troubleshooting.md)에 정리했다.

## 구현하면서 고민한 것들

### 주문

주문 요청에는 상품 ID와 수량만 받는다. 단가는 서버가 DB에서 다시 읽어서 계산한다. 요청 본문에 단가를 넣어 보내도 무시되는지 테스트로 확인했다.

거래처는 요청 값이 아니라 로그인 세션에서 꺼낸다. 다른 거래처 주문을 조회하거나 취소하려고 하면 403이 아니라 404로 응답한다. 403을 주면 그 번호의 주문이 있다는 사실은 알려 주는 셈이기 때문이다.

주문에는 주문 당시의 거래처 등급을 따로 저장한다. 나중에 등급을 바꿔도 지난 주문의 정산 기준이 흔들리지 않게 하기 위해서다.

주문번호는 `SO20261027-000001` 형식이고 뒷자리는 DB 시퀀스로 만든다. MyBatis는 같은 트랜잭션 안에서 같은 select를 다시 부르면 처음 결과를 캐시에서 돌려준다. 지금은 번호를 받은 뒤 바로 INSERT를 하고, 쓰기가 일어나면 캐시가 비워지기 때문에 문제가 되지 않는다. 그래도 나중에 쓰기 없이 번호를 여러 번 받는 코드로 바뀌면 같은 번호가 나올 수 있어서, 시퀀스 조회와 `FOR UPDATE` 조회에는 `flushCache="true"`를 걸어 두었다.

재고는 주문할 때가 아니라 관리자가 승인할 때 차감한다. 주문 시점에는 현재 재고를 넘는지만 확인하기 때문에, 각각은 재고 안이었던 주문 두 건 중 하나는 승인 단계에서 재고 부족으로 거절될 수 있다.

### 동시에 처리될 때

상태를 바꿀 때는 "조회하고 확인한 뒤 바꾸기"를 나누지 않고 `WHERE status = 'REQUESTED' AND version = ?` 조건을 건 UPDATE 한 번으로 처리한다. 영향받은 행이 0이면 다시 조회해서, 버전이 달라졌으면 "다른 사용자가 먼저 처리했다"고, 상태만 다르면 "지금 상태에서는 할 수 없다"고 구분해서 알려 준다.

승인과 승인 취소는 모두 주문 행을 먼저 잠그고, 상품 행은 ID 순서대로 잠근다. 잠금 순서를 한 가지로 맞춰서 서로 기다리는 상황을 피했다 ([ADR-006](docs/adr/006-approval-locking.md)).

상품 수정 화면에서도 재고를 덮어쓰지 않는다. 화면을 열어 둔 사이 승인으로 재고가 줄었는데 예전 숫자로 저장하면 재고가 되살아나기 때문이다. 수정 요청에 화면이 불러온 재고를 같이 받아서, 재고를 바꾸지 않았으면 재고 칼럼을 건드리지 않고, 바꿨으면 DB 재고가 그 값과 같을 때만 바꾼다. 다르면 409로 알린다 ([ADR-010](docs/adr/010-product-stock-compare-and-set.md)).

반품은 같은 주문 줄에 여러 건이 동시에 들어와도 주문 수량을 넘지 않아야 한다. 주문 줄을 `FOR UPDATE`로 잠근 뒤 반품 합계를 구하는데, 이 합계는 잠금과 같은 문장이 아니라 다음 문장에서 따로 조회한다. PostgreSQL 기본 격리 수준에서는 문장마다 새 스냅샷을 쓰기 때문에, 같은 문장에서 구하면 잠금을 기다리는 사이 다른 트랜잭션이 커밋한 반품이 합계에서 빠진다 ([ADR-007](docs/adr/007-return-qty-check.md)).

### 정산

정산은 `run_settlement` 프로시저가 한다. 해당 월의 기존 결과를 지우고 출고분과 반품분을 `INSERT ... SELECT`로 한 번에 넣은 뒤, 그걸 다시 거래처별로 합친다. 미리보기를 여러 번 해도 결과가 쌓이지 않고, 마감할 때도 최신 데이터로 한 번 더 계산한 다음 닫는다.

리베이트는 줄마다 출고일에 적용 중이던 요율로 계산하고 원 단위 미만은 버린다. 월 중간에 요율이 바뀌어도 그 전에 나간 출고는 이전 요율이 적용된다. 반품은 반품한 달에 마이너스로 들어가되, 리베이트는 원래 출고일 요율로 되돌린다. 그래서 9월에 출고하고 9월 정산을 마감한 뒤 10월에 반품이 들어와도 9월을 다시 열 필요가 없다. 한 줄을 여러 번 나눠 반품하면 반품마다 원 미만을 버린 끝전이 쌓여서 전량 반품해도 리베이트가 몇 원 남았는데, 지금은 출고 때 준 줄 리베이트를 누적 반품 수량 비율로 나눠 되돌려서 전량 반품하면 정확히 0이 된다 ([ADR-002](docs/adr/002-rebate-rate-and-returns.md)).

출고일에 적용할 리베이트 정책이 없는 주문이 하나라도 있으면 정산을 멈추고 주문번호를 알려 준다. 조인에서 조용히 빠지면 틀린 금액으로 마감되기 때문이다.

마감은 지난달까지만 허용했다. 진행 중인 달을 마감하면 남은 기간의 출고와 반품을 받을 수 없게 된다. 마감한 달에 속한 출고·반품 데이터는 서비스에서 먼저 막고, SQL을 직접 실행하는 경우까지 DB 트리거가 한 번 더 막는다. 트리거는 주문, 주문 줄, 반품, 리베이트 정책처럼 정산이 읽는 데이터 전체에 걸려 있다 ([ADR-003](docs/adr/003-closing-rules.md)).

출고일은 트랜잭션 시작 시각이라, 9월 30일 밤에 시작한 출고가 10월 1일에 커밋되는 사이 9월 마감이 끼어들 수 있다. 그대로 두면 마감된 9월에 정산에서 빠진 출고가 남는다. 정산월 단위 잠금으로 둘 중 먼저 시작한 쪽이 끝날 때까지 다른 쪽이 기다리게 했다. 출고가 먼저면 마감이 그 출고까지 포함하고, 마감이 먼저면 출고가 거부된다 ([ADR-009](docs/adr/009-settlement-month-lock.md)).

요율 변경도 비슷한 이유로 내일 이후 날짜만 받는다. 지난 날짜의 요율을 바꾸면 이미 출고된 주문의 정산 결과가 달라진다. 같은 등급의 적용 기간이 겹치지 않는 것은 PostgreSQL `EXCLUDE` 제약으로 보장한다.

정산이 실패한 기록은 실행 이력 테이블에 남기지 않고 애플리케이션 로그로만 남겼다. 처음에는 별도 트랜잭션(`REQUIRES_NEW`)으로 남기려고 했는데, 그렇게 하면 서로 기다리다 멈추는 경우가 있었다 ([ADR-005](docs/adr/005-no-requires-new-failure-log.md)).

정산 결과는 CSV로 내려받을 수 있다. 엑셀에서 열었을 때 한글이 깨지지 않도록 UTF-8 BOM을 붙였고, `=`, `+`, `-`, `@`로 시작하는 값은 엑셀이 수식으로 실행하지 않도록 앞에 작은따옴표를 붙였다.

### 로그인

세션 기반으로 하고, React가 `XSRF-TOKEN` 쿠키 값을 읽어 `X-XSRF-TOKEN` 헤더로 보내는 방식으로 CSRF를 막는다. 개발할 때는 Vite 프록시로 화면과 API를 같은 출처로 묶어서 CORS 설정 없이 쿠키를 쓴다 ([ADR-008](docs/adr/008-session-and-csrf.md)).

로그인에 성공하면 세션 ID를 새로 발급한다. 없는 아이디, 틀린 비밀번호, 거래가 중지된 거래처 계정은 모두 같은 메시지로 응답한다. 응답 시간도 맞췄다. Spring Security는 기본적으로 비밀번호를 확인하기 전에 계정 상태부터 봐서, 거래 중지 계정은 비밀번호 비교 없이 바로 실패해 응답이 빨랐다. 메시지가 같아도 시간으로 계정 상태가 드러나기 때문에, 계정 상태 검사를 비밀번호 확인 뒤로 옮겼다.

### 시간대

날짜 계산은 한국 시간 기준으로 고정했다. 애플리케이션은 `Clock` 빈으로 "오늘"과 "이번 달"을 구하고, DB 세션도 접속할 때 `SET TIME ZONE 'Asia/Seoul'`로 맞춘다. CI 서버처럼 UTC로 도는 환경에서도 출고일이 다른 달로 넘어가는 일이 없다.

## 테스트

테스트 68개 중 통합 테스트 64개가 실제 PostgreSQL 컨테이너 위에서 돈다. PostgreSQL 전용 기능(`EXCLUDE` 제약, 프로시저, 트리거)을 쓰고 있어서 H2 같은 메모리 DB로는 확인할 수 없기 때문이다.

컨테이너와 Spring 컨텍스트는 테스트 전체에서 한 번만 띄우고, 테스트마다 트랜잭션을 걸었다가 롤백한다. 테스트 클래스마다 컨테이너를 새로 띄우지 않아서 금방 끝난다.

| 종류 | 대표 테스트 | 확인하는 것 |
|---|---|---|
| 로그인·권한 | `AuthIntegrationTest` | 세션 유지, CSRF 없는 요청 거부, 권한별 접근 |
| 기준정보 | `ProductAdminIntegrationTest`, `RebatePolicyIntegrationTest` | 상품 코드 중복, 검색어 이스케이프, 요율 변경 규칙 |
| 주문 | `MarketOrderIntegrationTest`, `AdminOrderIntegrationTest` | 단가 조작 무시, 다른 거래처 주문 숨김, 상태 전이, 부분 반품 |
| 정산 | `SettlementIntegrationTest` | 월 중간 요율 변경, 반품월 차감, 마감 후 재실행 차단, 트리거 |
| 동시성 | `ConcurrencyIntegrationTest` | 동시 승인, 같은 주문 중복 승인, 승인과 취소 경합, 동시 반품 |
| 월 경계 | `SettlementMonthBoundaryTest` | 출고와 마감이 겹칠 때 어느 쪽이 먼저든 정산에서 빠지는 출고가 없음 |
| 로그인 시간 | `LoginProviderTest` (단위) | 계정 상태와 상관없이 모든 실패가 비밀번호 비교를 한 번 치름 |

동시성 테스트와 월 경계 테스트는 테스트 트랜잭션 없이 돈다. 스레드마다 실제로 커밋해야 잠금이 경쟁하기 때문이다. 대신 끝나면 만든 데이터를 직접 지운다.

| 시나리오 | 결과 |
|---|---|
| 재고 10개 상품의 1개짜리 주문 20건을 동시에 승인 | 10건 승인, 10건 재고 부족, 남은 재고 0 |
| 같은 주문을 관리자 5명이 동시에 승인 | 1건만 승인, 재고도 한 번만 차감 |
| 거래처 취소와 관리자 승인이 동시에 (10쌍) | 주문마다 하나만 반영, 재고 = 처음 재고 - 승인 건수 |
| 수량 5개인 줄에 1개씩 반품 10건을 동시에 등록 | 5건만 등록 |

## 성능

### 정산 프로시저

거래처 200곳, 상품 500개를 만들고 6개월 동안 매달 출고 라인 10만 건(총 60만 건), 반품 1%를 넣은 뒤 3월분 정산 시간을 쟀다. 측정 스크립트는 단계마다 트랜잭션 안에서 구조를 바꾸고 3번 실행한 뒤 롤백한다.

```bash
docker exec -i minierp-postgres psql -U minierp -d minierp < db/seed/perf_seed.sql
docker exec -i minierp-postgres psql -U minierp -d minierp < db/perf/measure_settlement.sql
```

환경: Windows 11 노트북, Intel Core i3-1315U, RAM 8GB, Docker Desktop PostgreSQL 16

처음에는 정산용 인덱스(출고일, 반품일)를 넣으면 빨라질 거라고 생각했다. 그런데 인덱스가 있든 없든 2초 안팎으로 비슷했고, 오히려 인덱스가 있을 때 조금 더 느렸다.

그래서 프로시저 안의 문장을 하나씩 떼어서 `EXPLAIN ANALYZE`로 봤다. 출고·반품 데이터를 읽어 오는 조회는 0.2초 정도로 빨랐다. 시간을 잡아먹던 건 정산 상세 테이블에 10만 행을 넣을 때 행마다 실행되는 외래키 확인 두 개였다. 이게 전체의 절반이 넘었다.

정산 상세는 프로시저만 만드는 파생 데이터고, 실행할 때마다 지우고 다시 만든다. 값도 이미 외래키가 걸린 주문과 정산월 테이블에서만 가져온다. 외래키를 빼도 잘못된 참조가 생길 경로가 없다고 보고 제거했다. 행이 거래처 수만큼(수백 건)밖에 없는 거래처별 합계 테이블에는 그대로 뒀다 ([ADR-004](docs/adr/004-settlement-detail-without-fk.md)).

| 단계 | 구조 | 소요 시간 (3회 중 가운데 값) |
|---|---|---|
| 1 | 정산용 인덱스 없음, 상세 외래키 있음 | 1.95초 (1.95 / 1.78 / 1.98) |
| 2 | 정산용 인덱스 추가 (V4) | 2.27초 (2.41 / 2.27 / 2.17) |
| 3 | 상세 외래키 제거 (V5, 현재) | 1.16초 (1.06 / 1.16 / 1.25) |

처리 건수는 약 10만 건이고, V4에서 V5로 바꾸면서 실행 시간이 약 49% 줄었다.

이후 마감월 보호를 넓히고(V6) 정산월 잠금(V7)과 반품 리베이트 배분(V8)을 넣은 뒤에도, 같은 데이터로 V5와 비교해서 정산 시간이 늘지 않았고 금액·건수도 같은 것을 확인했다. 대신 주문 줄에 행 트리거가 생겨서 `perf_seed.sql`로 60만 줄을 넣는 시간은 약 30% 늘었다.

인덱스로 빨라지지 않은 건, 6개월치 중 한 달치(약 17%)를 고르는 조건이라 인덱스로 골라 읽는 것과 테이블 전체를 읽는 것의 차이가 작기 때문으로 본다. 측정 순서나 캐시 상태에 따른 오차도 섞여 있을 수 있어서 "효과가 없었다"까지만 판단했다. 이력이 몇 년치로 쌓이면 전체를 읽는 비용은 계속 늘지만 한 달치를 읽는 비용은 그대로라, 인덱스는 지우지 않았다.

### 동시 승인 (k6)

HTTP 계층(세션, CSRF, 커넥션 풀)까지 포함해서, 재고 100개 상품에 주문 200건을 넣고 관리자 50명이 동시에 승인했다. 실행 방법은 [load-test/README.md](load-test/README.md)에 있다.

| 항목 | 값 |
|---|---|
| 승인 / 재고 부족(409) / 예상 외 응답 | 100건 / 100건 / 0건 |
| 남은 재고 | 0개 |
| 승인 200건 처리 시간 | 3.6초 (건당 약 18ms) |
| 승인 응답 시간 | 중앙값 733ms, p95 1.08s |
| 로그인 응답 시간 | 중앙값 477ms, p95 722ms |

초과 판매 없이 재고만큼만 승인됐다.

처음 돌렸을 때는 전체 응답 시간 p95가 2.97초로 나와서 놀랐는데, 그 숫자에는 준비 단계의 주문 200건, 로그인, 마지막 확인용 조회까지 다 섞여 있었다. 요청 종류별로 태그를 붙여 다시 쟀더니 위 표처럼 나왔다.

승인이 느린 건 모든 요청이 같은 상품의 재고 행 잠금을 차례로 기다리기 때문으로 본다. 200건이 3.6초 걸렸으니 한 건에 약 18ms이고, 50명이 동시에 보내면 평균 25~40번째쯤 줄을 서게 되니 0.45~0.7초가 나온다. 측정된 중앙값과 비슷하다. 초과 판매를 막으려고 일부러 한 줄로 세운 결과라 그대로 뒀다. 같은 상품에 승인이 수십 건씩 동시에 몰리는 일은 드물기도 하다. 로그인이 느린 건 50명이 동시에 BCrypt 비밀번호 확인을 하면서 CPU가 몰렸기 때문이다.

## 트러블슈팅

실행하고 측정하면서 실제로 막혔던 문제 6건과, 코드 리뷰에서 다시 찾은 정합성 문제 5건을 [docs/troubleshooting.md](docs/troubleshooting.md)에 정리했다. 최신 Docker Desktop에서 Testcontainers가 Docker를 못 찾은 일이나, k6 부하 테스트가 두 번째 요청부터 전부 403으로 실패한 일 같은 것들이다.

## 아직 남은 것

실제 업무에 쓰려면 아래 작업이 더 필요하다.

- 정산 마감을 되돌리는 기능이 없다. 잘못 마감하면 DB를 직접 고쳐야 한다. 실무라면 권한 있는 사람만 쓸 수 있는 마감 해제와 그 이력이 필요하다
- 재고는 상품 수정 화면에서 숫자로 바꾼다. 승인과 겹쳐 덮어쓰는 문제는 막았지만, 입고·조정 같은 재고 이력이 없다
- 같은 상품에 승인이 몰리면 한 줄로 처리돼서 대기 시간이 길어진다. 그런 업무라면 재고 행을 나누거나 요청을 모아 처리하는 방식을 검토해야 한다
- 세션이 서버 메모리에 있어서 서버를 여러 대 띄우려면 Spring Session(Redis 등)으로 옮겨야 한다
- 로그인 시도 제한, 비밀번호 변경, 사용자 관리 화면이 없다
- 정산 결과는 CSV로만 내려받는다. 주문 목록은 대량 데이터에서 조회 속도를 재 보지 않았다
- 프론트엔드에는 자동 테스트가 없다. 화면은 직접 눌러 보면서 확인했다
